## 2. Найденные и исправленные проблемы

### 2.1. Несовместимость heartbeat writer/watchdog

Фоновый Chat Monitor записывает heartbeat в JSON-формате с полем `ts` и метриками воркеров, а watchdog ранее пытался разобрать весь файл как обычный ISO timestamp. В результате рабочий heartbeat считался повреждённым, что мог приводить к ложным аварийным уведомлениям.

Исправлено в `scripts/check_heartbeat.py`: watchdog теперь принимает актуальный JSON-формат и сохраняет обратную совместимость со старым plain-text ISO timestamp. Дополнительно обработан случай ошибки чтения файла, при котором переменная с содержимым могла быть не инициализирована.

Добавлены регрессионные тесты для JSON heartbeat, legacy timestamp и повреждённого payload.

### 2.2. Ложное production-предупреждение об allowlist

В `utils/config_validator.py` предупреждение `ALLOWED_USER_IDS не задан` находилось в ветке `else` проверки провайдера LLM. Поэтому при production-конфигурации с Anthropic предупреждение могло появляться даже при корректно заданном allowlist.

Лишняя ветка удалена. Реальная проверка пустого allowlist в production сохранена в fail-closed режиме: при отсутствии `ALLOWED_USER_IDS` запуск блокируется.

### 2.3. Устаревшие тестовые фикстуры

После усиления security-контракта `create_chat_lead()` требует обязательный `message_id`, чтобы дедупликация Telegram-сообщений не отключалась через `NULL`. Шесть тестов создавали chat-lead без этого идентификатора и падали.

Фикстуры обновлены без ослабления production-проверки. В рабочем коде `chat_monitor/processor.py` `message_id` уже передавался корректно.

## 3. Анализ логов и runtime-артефактов

В репозитории не обнаружены файлы с расширениями `.log`, `.out` или `.err`, поэтому полноценного исторического журнала приложения для анализа нет. Были проверены доступные диагностические артефакты.

`chat_monitor.heartbeat` содержит корректный JSON с `workers_alive=2`, `queue_size=0` и `worker_restarts=0`, однако timestamp последнего heartbeat — **2026-08-18**, то есть на момент аудита он устарел примерно на несколько дней. Это означает, что Chat Monitor сейчас не следует считать работающим 24/7: перед запуском необходимо стартовать процесс и убедиться, что heartbeat обновляется.

Старые `.tmp_fail.txt` и `.tmp_test_out.txt` содержали ошибки прежнего состояния тестов с отсутствующим `message_id`; после исправлений полный прогон проходит успешно.

## 4. Проверка готовности к запуску

Контейнерный healthcheck в текущем окружении пройден: BOT_TOKEN распознаётся, Telegram API отвечает, SQLite-схема готова, Redis доступен.

Production readiness намеренно не объявлен успешным, потому что текущая конфигурация не выставлена в `ENVIRONMENT=production`. Это безопасное поведение: нельзя автоматически менять production-флаги, токены, ключи шифрования, PostgreSQL или allowlist без подтверждённых значений владельца.

Перед боевым запуском необходимо выполнить следующие действия:

1. Задать `ENVIRONMENT=production`.
2. Проверить `ALLOWED_USER_IDS` и убедиться, что там только необходимые Telegram ID.
3. Использовать PostgreSQL и Redis для production-контура.
4. Указать отдельные валидные `PII_ENCRYPTION_KEY` и `BACKUP_ENCRYPTION_KEY`.
5. Установить `AUTO_CREATE_SCHEMA=false` и выполнить `alembic upgrade head`.
6. Указать `SECRETS_ROTATED_AT` после ротации токена бота, LLM-ключа и Telethon session.
7. Запустить бота и Chat Monitor, затем убедиться, что `chat_monitor.heartbeat` обновился и содержит свежий `ts`.
8. Повторно выполнить `python -m scripts.production_readiness` в production-окружении.
