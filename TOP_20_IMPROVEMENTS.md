# CLOUD-BOT: 20 лучших улучшений по итогам аудита

**Дата аудита:** 22 августа 2026 года  
**Текущий контекст:** Telegram-бот на aiogram, асинхронный SQLAlchemy, SQLite для разработки, PostgreSQL/Redis для production, LLM-интеграции, OpenStreetMap/Overpass, Chat Monitor через Telethon, фоновые задачи reminders и retention.

## Краткий вывод

Проект уже имеет сильную основу: owner-scoping, allowlist, PII-шифрование, retention, миграции Alembic, Redis-координацию, bounded retries, healthcheck и тестовый контур. Последняя проверка показала **337 успешных тестов и 83% покрытия**. Главные оставшиеся риски лежат не столько в базовой функциональности, сколько в production-эксплуатации: ротации скомпрометированных секретов, контроле Git-истории, end-to-end проверке PostgreSQL/Redis, наблюдаемости, идемпотентности фоновых процессов и несогласованности документации.

## Детализация рекомендаций

### P0 — сделать до любого боевого rollout

**1. Завершить ротацию всех скомпрометированных секретов.** История проекта ранее содержала признаки утечки BOT_TOKEN, LLM-ключей, Telethon session и локальных данных. Необходимо отозвать старые значения, выпустить новые, создать новую Telethon session, обновить production secret store и установить `SECRETS_ROTATED_AT`. Проверка успеха — старые значения не работают, новый smoke test проходит, секреты не выводятся в CI-логи.

**2. Полностью закрыть incident-response по Git-истории.** Одного удаления файлов из рабочей директории недостаточно. Нужно проверить refs, tags, releases, CI artifacts, caches и старые клоны, затем зафиксировать результат в incident log. В дальнейшем следует добавить pre-commit и CI secret scanning, запрещающий архивы с session-файлами, `.env`, базами и ключами.

**3. Выполнить реальный production E2E-прогон PostgreSQL + Redis.** Локальный SQLite healthcheck не подтверждает production-путь. Следует поднять disposable PostgreSQL/Redis stack, применить `alembic upgrade head`, запустить мигратор и бота, проверить `/start`, поиск, сохранение лида, LLM-анализ, reminder, retention, backup и восстановление. Этот прогон должен стать обязательным release candidate тестом.

**4. Ввести blocking CI-gates для качества и безопасности.** В CI должны блокировать merge: полный pytest, branch coverage threshold, Ruff, Mypy, `pip-audit`, проверка хэшей зависимостей, secret scanning, проверка миграций и сборка Docker image. Mypy особенно важно сделать blocking, поскольку сейчас типовые ошибки могут пройти в main.

**5. Сделать production readiness частью CI/CD.** `scripts.production_readiness` должен запускаться перед деплоем и проверять environment, allowlist, PostgreSQL, Redis, ключи шифрования, миграции, ротацию секретов и отсутствие исторических секретов. Deploy должен останавливаться при любом `[ERROR]`, а результат проверки сохраняться как артефакт без раскрытия значений.

### P1 — повысить надёжность и наблюдаемость

**6. Добавить централизованное структурированное логирование.** Перейти от разрозненных текстовых сообщений к JSON-логам с `timestamp`, `level`, `event`, `request_id`, `owner_hash`, `lead_id` и `duration_ms`. Токены, телефоны, usernames, тексты сообщений и промпты должны проходить redaction до записи. Нужны уровни INFO/WARNING/ERROR и политика retention логов.

**7. Внедрить метрики и алерты по ключевым SLO.** Минимальный набор: успешные/ошибочные Telegram updates, latency внешних API, Overpass 429/5xx, LLM latency и budget, размер Chat Monitor queue, worker restarts, reminder lag, DB pool saturation и backup age. Алерты должны реагировать не только на процесс, но и на отсутствие полезной работы.

**8. Усилить supervisor фоновых задач и Chat Monitor.** Для каждой фоновой задачи нужны отдельные heartbeat, last-success timestamp, restart counter и backoff с верхним пределом. Если воркер многократно падает, система должна перейти в degraded state и отправить один агрегированный alert, а не бесконечно спамить владельца. Текущий JSON heartbeat уже является хорошей базой для этого улучшения.

**9. Перевести напоминания на надёжную distributed-очередь.** При нескольких экземплярах бота нужно атомарно claim-ить reminder через PostgreSQL lock/claim token, хранить `attempt_count`, `next_attempt_at`, `last_error` и idempotency key для Telegram send. Отметку `is_sent` лучше заменить на явную state machine: pending → claimed → sent/failed/dead-letter.

**10. Разделить liveness и readiness endpoints.** Liveness должен отвечать, что процесс жив и event loop работает. Readiness должен проверять БД, Redis, применённую схему и критичные конфигурационные зависимости. Это предотвращает отправку трафика в процесс, который запущен, но не способен обслуживать команды.

**11. Добавить полноценную миграционную и backup/restore стратегию.** Нужны регулярные encrypted backups, проверка checksum, retention policy, автоматическое восстановление в disposable database и периодический disaster-recovery drill. Для PostgreSQL следует отдельно тестировать SQL dump/restore, а для SQLite — restore и последующий `verify_schema`.

**12. Усилить защиту LLM-контуров от prompt injection и утечек.** Внешние данные OSM, Telegram и сайты нужно передавать модели как недоверенные поля с чётким разделением system/developer/user content. Следует фильтровать инструкции из данных, ограничивать размер и тип контента, запрещать модели выполнять действия, не требуемые сценарием, и redaction-ить телефоны/PII в telemetry.

**13. Ввести строгую схему LLM-ответов и версионирование промптов.** Использовать JSON Schema/Pydantic validation с диапазонами score, обязательными полями, максимальными длинами и reject-on-extra-risky-content. Для каждого вызова хранить `prompt_version`, `model`, `provider`, latency и validation result, но не сохранять полный PII-содержащий prompt без необходимости. Изменение промпта должно сопровождаться regression fixtures.

**14. Сделать внешние интеграции адаптивными к rate limits.** Помимо bounded retries нужны per-provider circuit breaker, jitter, concurrency limits, budget guard и отдельная обработка постоянных 4xx. Для Overpass следует использовать резервные endpoint strategy только при соблюдении правил сервиса, а для Telegram — контролировать flood limits и retry-after.

### P2 — продуктовые и архитектурные улучшения

**15. Оптимизировать Overpass-поиск и кэширование.** Нормализовать город/категорию, добавить bounded cache с Redis, ограничить размер ответа, дедуплицировать объекты по OSM ID и сохранять время/источник выдачи. Это уменьшит повторные запросы, задержки и вероятность блокировок API.

**16. Добавить часовые пояса и локализованные напоминания.** Сейчас пользовательский сценарий опирается на UTC. Следует хранить timezone per owner, показывать локальное время при создании reminder, учитывать DST и иметь безопасный fallback на UTC. Это напрямую повысит полезность CRM.

**17. Разделить FSM-сессии, кэш и долгоживущие данные.** Большие результаты поиска и generated messages не следует хранить целиком в FSM. Лучше сохранять search session в БД/Redis по короткому TTL, передавать в callback только opaque ID, ограничивать размер сериализованных данных и очищать abandoned sessions.

**18. Повысить качество CRM-модели и поиска дублей.** Добавить нормализованные поля для телефона, домена, OSM ID, Telegram username и адреса; использовать составные индексы и fuzzy duplicate review. Дедупликация должна учитывать смену username, разные написания адресов и повторные импорты из нескольких источников.

**19. Удалить устаревшие документы и ввести single source of truth.** В репозитории много исторических отчётов с расходящимися числами тестов и статусами readiness. Нужно оставить актуальные `README`, `DEPLOYMENT`, `SECURITY`, `OPERATIONS` и `CHANGELOG`, автоматически генерировать coverage/readiness status и пометить архивные документы как historical.

**20. Добавить безопасный административный контур и аудит действий.** Для multi-user режима нужны роли, owner/admin separation, управление allowlist без ручного редактирования `.env`, ротация ключей, просмотр failed jobs и audit trail административных операций. Каждое изменение статуса, удаление лида, экспорт и повтор LLM-анализа должны иметь actor, timestamp, object и result.

## Три улучшения с максимальной отдачей

Если выбирать только три направления, сначала следует завершить **ротацию секретов и очистку Git-инцидента**, затем провести **реальный production E2E-прогон PostgreSQL/Redis**, а после этого включить **blocking CI-gates и наблюдаемость**. Именно эти действия сильнее всего сокращают вероятность дорогостоящего сбоя при минимальном изменении пользовательского функционала.
